## Goals / Non-Goals

**Goals:**
- No credential in plain text in any cloud record (command params, `command_events`, shadows, shadow history, logs).
- A captured envelope cannot be retargeted, moved to another device, replayed after a newer one, or replayed after a delete.
- A secret can only reach the one LAN endpoint it was bound to: its ip:port, and for an on-link target also its MAC, checked against ARP before the first byte of every request that expands it. Residual, accepted: a routed (off-link) target cannot be MAC-bound and matches by ip:port only.

**Non-Goals:**
- Protection against an operator who holds gateway command rights. Such an operator can already drive the bound equipment through `${secret:...}` and could try reflection tricks on the target; the echo scrub is best effort. Rights are an IAM question (lan-tunnel 5.1 / 5.2 follow-ups).
- Encryption at rest, flash encryption, eFuses (manufacturing ADR-6).
- Physical attackers (flash dump yields `key_pem` and the slots alike).
- The HTTPS module itself (add-gateway-modules). Secrets expand into `https` only on a product where that module's bench gate has passed; until then the executor's module availability check returns `MODULE_UNAVAILABLE` before expansion, and plain `http` is the fallback. With plain HTTP the expanded secret crosses the LAN in clear, as it does when a person uses that equipment's web UI.
- Web UI.

## Decisions

### D1. One blob per slot, fixed keys `s00`-`s15`
NVS key names are limited to 15 characters and secret names to 24, so the name lives inside the blob and lookup scans the 16-entry RAM cache. One `setBlob` per rotation is atomic in ESP-IDF NVS (new entry written, old erased), so a power loss leaves either the old or the new value. The slot carries an optional bound MAC (6 bytes, all zero when absent, which is never a valid MAC, so no flag byte is needed). 16 slots × at most 304 B ≈ 11 NVS entries each, about 5.6 KB worst case of the shared 64 KB partition. Alternatives: one key per field (non-atomic rotation, more entries), one blob for the whole store (every rotation rewrites 4.9 KB, larger wear and failure window).

### D2. Namespace in the excluded list plus explicit factory-reset clear
Adding `secrets_ns` to `EXCLUDED_NVS_NAMESPACES_LIST` removes it from backup and restore in one place but also from `clearAllPreferences()`, so `_factoryReset()` clears it explicitly next to `auth_ns`. It is also added to `TO_INITIALIZE_NVS_NAMESPACES_LIST`. `Secrets::begin()` runs after `createAllNamespaces()` and before the gateway and MQTT start.

### D3. Envelope v1 and an authenticated `issued_at`
RSA-OAEP-SHA256 key wrap plus AES-256-GCM, as decided in the brief. The brief's AAD `energyme-secret-v1|<device_id>|<name>|<ip:port>` is extended with `|<mac>|<issued_at>`: a freshness value or a MAC binding outside the AAD could be rewritten or stripped by whoever replays the envelope, so it would protect nothing. An absent MAC is the empty field. `kid` (AWS certificate id = SHA-256 of the cert DER) lets the device reject an envelope for another key before a costly RSA operation and lets the tool pick the right certificate when a thing has several principals; the device computes it once at `Secrets::begin()` from `cert_pem`. All crypto failures map to one code so the device is not a padding or tag oracle. Never PKCS#1 v1.5 (Bleichenbacher). The plaintext is `len` u16 + value + zero padding to 258 bytes, so the archived `ct` (always 258 bytes) does not reveal the value length; the device checks `len` and the padding after authentication. Values must be strict UTF-8 without NUL, CR, LF, which keeps raw expansion from injecting header lines and gives `|json` a defined result.

Device implementation notes, all covered by tasks: read `key_pem` into its own zeroized PSRAM buffer per operation, never borrow `_awsIotCorePrivateKey` (other task, no mutex, wiped on reconnect); `mbedtls_pk_parse_key` length is `strlen + 1` for PEM; pass a CTR-DRBG as `f_rng` (blinding is mandatory in mbedTLS 3.x); call `mbedtls_rsa_set_padding(rsa, MBEDTLS_RSA_PKCS_V21, MBEDTLS_MD_SHA256)` before decrypt, else it silently uses v1.5; require the unwrapped length to be exactly 32; `mbedtls_gcm_auth_decrypt` with a 16-byte tag; `mbedtls_platform_zeroize` on key, plaintext and PEM buffers; `mbedtls_pk_free` on every path.

### D4. Replay: namespace-wide high-water mark plus freshness window
A per-name counter does not survive delete (an old envelope would resurrect a deleted secret) and per-name tombstones would eat slots. One persisted `hwm` makes every envelope applicable at most once device-wide; deletes push it to `now`, so in-flight envelopes issued before a delete die too. The freshness window (900 s back, 300 s ahead) bounds an envelope that was never applied and limits the factory-reset case, where `hwm` returns to 0. The command `created_at` (mandatory in the deployed template, energyme-infra `projects/energyme-home-iot-pipeline/cdk/constructs_/iot_commands.py:213,219`) is not authenticated, since whoever dispatches sets it, so the replay rules never rely on it. Idempotent repeat is checked before `hwm` so AWS redelivery of the same execution reports success. The cost is that two names set in the same second collide; the device returns `hwm=<n>` in the `SECRET_STALE` description and the tool retries once with `issued_at = hwm + 1`, without waiting for the shadow.

`hwm` ceiling: the device takes NTP from the LAN gateway first (`source/src/customtime.cpp`, comment above `_configureNtpServers`), `TimeFloor::onAnswer` accepts any valid future candidate and only caps the persisted floor (`source/lib/time_floor/time_floor.cpp:40-49`), and a manual set can also move the clock (`customtime.cpp:255`). Without a ceiling, one wrong-future answer plus one delete would push `hwm` years ahead and make every later envelope `SECRET_STALE` (and its retry `SECRET_CLOCK_SKEW`) until a factory reset. So before every replay decision, delete and local set, with the clock synchronised, a `hwm` above `now + 300` is lowered to `now + 300`, persisted and logged at WARNING; this also undoes a boot-time raise from a future `set_at`. At the decision it widens nothing, since any `issued_at` above `now + 300` is already `SECRET_CLOCK_SKEW`. Residual, accepted: an envelope applied while the clock was wrong-future carries that future `issued_at`, and could be replayed inside its 900 s window when real time reaches it if no later set or delete has passed it; after a clock incident (the WARNING) the operator rotates the affected secrets. `SECRET_CLOCK_SKEW` also carries `hwm=<n>`, so the tool waits at most about 310 s for its clock to reach `hwm + 1` and retries, or exits with the difference. Alternatives: device nonce challenge (extra round trip, no command support for it), per-name counters (delete hole).

### D5. Ops run in the gateway task, under the existing switches
The RSA private operation (expected tens to a few hundred ms) must not run on the MQTT task, so both ops go through `Gateway::submit()` as new `GatewayLogic::Op` values, dispatched by the add-gateway-modules command adapter (they open no socket, so they are not executor modules), and use the existing slot (with whatever busy rule `lan-gateway` specifies at the time, `GATEWAY_BUSY` today, possibly a bounded wait after add-lan-collector) and kill switch (`GATEWAY_DISABLED`). The `lan-gateway` envelope requirement is not modified in this change because three other changes touch it; the op list is extended by an ADDED requirement in `gateway-secrets`, and the `UNKNOWN_OP` description string in `mqtt.cpp` grows. This change requires add-gateway-modules, so the ops are written against its adapter, not today's `_run()` switch. Local REST management works with the gateway disabled (local admin; values are inert while the gateway is off).

### D6. A `secret` resolver in the one engine, gated on module and target
There is one tokenizer, the add-gateway-modules engine, so the binding check always runs on the same parse as the expansion. `secrets_logic` holds no grammar; it provides the resolver decision (`decide(module, ip, port, arg, cache)` returning a slot or a reason code) and the scrub, both pure and host-tested. The resolver is never registered globally. The engine takes a per-call `Resolver*` chain (add-gateway-modules D7): the command adapter passes the `secret` resolver alone and the collector appends it after its own `now`, `cursor`, `var` and `cap` resolvers, so collector names stay `BAD_TEMPLATE` in one-shot commands. The executor passes module, target IPv4 and effective port in the resolver context (MODIFIED `gateway-modules` requirement, which also lets the resolver return its own reasonCode instead of `BAD_TEMPLATE`). The resolver answers only for `http` and `https`, one-shot or collector step; for `tcp` it fails with `SECRET_MODULE_NOT_ALLOWED`, because a raw TCP reply has no defined structure to scrub and a `tcp` grant covers the whole target. `udp`, `modbus_tcp` and tunnel bytes are never templated by the engine, so a secret cannot reach them. On success it reads the value from NVS into a PSRAM scratch, hands it to the engine (which applies the up to 3 encodings into its zeroized output buffer), records the token's name and final encoded form for the scrub, and zeroizes the scratch. The engine grammar is followed as is: `$${` escape, chained encodings, `BAD_TEMPLATE` for malformed placeholders, untemplated fields (`body_b64`, header names) sent literally, which is safe since nothing is resolved there. A cap of 8 `secret` placeholders per request bounds NVS reads. Rejected: a secrets-specific tokenizer (two parsers can disagree, and its field list and `BAD_ARGS` rule contradicted the engine), allowing `tcp` (unscrubbable reply).

### D6a. MAC binding on the slot, enforced on every request that expands it
An ip:port binding fails open on DHCP LANs: once the meter or XWEB is renumbered, whatever host takes its address receives the credential on the next poll. add-gateway-modules MAC-checks only requests that need a grant or a read declaration, so a polled GET with `Authorization: Basic ${secret:meter_basic|b64}` would never be checked. The slot therefore carries an optional `mac`, set by `secret_set` (inside the AAD) or local REST, and the rule follows `Target MAC binding` of add-gateway-modules, applied to the secret instead of the entry. The executor passes the on-link flag (from `ip4_route` and the interface netmask, at run time) in the resolver context. On-link without a slot MAC is `SECRET_TARGET_MISMATCH` with `MAC_REQUIRED` before any socket and before the NVS read. MAC-bound but now off-link is `SECRET_TARGET_MISMATCH` with `TARGET_MAC_CHANGED` before any socket. MAC-bound and on-link makes the resolver require the executor's ARP compare (the add-gateway-modules helper, its task 4.3a), which runs after connect and before the first byte (before the ClientHello for `https`) whatever the access class. Like grants, the store never decides on-link status at set time, because the network can change; the tool warns when `--mac` is missing. Alternatives: MAC-check only the request classes add-gateway-modules already checks (leaves the GET hole open), require a MAC at set time (decides on-link status at the wrong moment and breaks routed targets).

### D7. Echo scrub, best effort
LAN equipment often echoes form fields in error pages, and results land in `command_events` forever. For each expanded token the raw value and the final encoded form of its chain (each if at least 4 bytes) are replaced in status line, headers and body with `${secret:<name>}`; for `https` this runs on the decrypted reply. Intermediate forms of a chain (the `|url` text inside `|url|b64`) are not scrubbed, since they never went on the wire. Values shorter than 4 bytes are not scrubbed (too many false hits). Transformed reflections (HTML-escaped, case-changed) are not caught; see Non-Goals.

One layer owns the secret scrub, the executor. The result scrub of the `secret` resolver is registered with the executor, the only registration this change makes, and the executor runs it before `run` returns, so the command adapter and collector steps get the same scrubbed `ExecResult` plus a boolean `redacted`. The adapter publishes it as `redacted: "true"`. The collector never scrubs secrets a second time; it OR-s `redacted` into its part header `rd` and runs the same pure function only for its own `${cap:x}` values (add-lan-collector D5). A second secret pass would find nothing left, so `rd` would lose the replacement signal, which is why the flag travels in the result.

The scrub never grows a buffer. A placeholder (up to 34 bytes) is longer than the value it replaces (at least 4), up to 8.5 times per match, while add-gateway-modules D5 allocates `body` as exactly `max_bytes` and commands publish at most 4096 bytes. So the output is bounded by the cap of the buffer being scrubbed (2048 for the header block, `max_bytes` for the body, which is 4096 for commands and the job's `max_bytes` for collector steps). Past the cap the output is cut with `truncated` set, a placeholder that would straddle the cut is dropped whole, and the cut-prefix rule then removes any partial scrubbed form, so neither a partial value nor a partial placeholder is published. The command cap, the collector byte quota and its 128 KB part ceiling therefore stay as they are. The implementation is free (in place, moving bytes back to front after a forward pass that finds the matches and the cut, or a bounded scratch), as long as it writes nothing past the buffer; host task 2.5 checks a 4096-byte body of repeated 4-byte echoes. Rejected: a same-length mask such as `****` (keeps the length, but the decoder loses which secret was echoed and a 4-byte value cannot be told from a coincidence), and reallocating a larger buffer (breaks the caps above).

### D8. Metadata in the `system` shadow
Reported-only object `secrets` in `system`. Reasons: drift detection already rebuilds `system` every 3 s (`shadow.cpp:409-416`), so local REST changes reach the cloud with no new plumbing; the gateway switches already live there (`shadow.cpp:655-658`); `system` is already in infra `KNOWN_SHADOWS`, so no infra change; shadow history in Iceberg gives a rotation audit trail with metadata only. A delta on `secrets` goes through the existing unknown-field path (nulled, WARNING). Rejected: `info` (reported-only but not drift-checked, a local change waits for the next reconnect), `collector` (belongs to add-lan-collector, wrong layer, its own 2 KB reported budget), command results only (no standing view for the tool to read `kid` and `hwm`).

Size of the whole `system` document. The AWS limit is 8192 bytes of state per named shadow. This design assumes `desired` and `reported` count together, the conservative reading add-lan-collector also adopts (its open question), so a looser reading needs no change. Worst case, compact JSON:

- `desired` while the cloud writes a full grant list: `gateway_write_grants` at its 3072 B cap (add-gateway-modules) plus keys, about 3.1 KB.
- `reported` `gateway_write_grants`: the old list, also up to 3072 B plus key, about 3.1 KB.
- `reported` fields of `_reportSystem()` (`shadow.cpp:645-658`: brightness, two send flags, two publish limits, three log levels, two switches) about 0.28 KB, `tunnel_ports` with 16 five-digit ports about 0.11 KB, `tunnel_active` with a session about 0.12 KB. About 0.51 KB together.
- `reported` `secrets`: header with the 64-hex `kid` and `hwm` about 0.11 KB, plus 16 slots as `[name, "ip:port", set_at, m]` with 24-character names, 15-character IPs and 5-digit ports at 65 B each, about 1.04 KB. At most 1.2 KB.

Total about 7.9 KB, under 8192 B by roughly 0.3 KB. A keyed slot object with the MAC (`{name, ip, port, mac, set_at}`, about 118 B) would make `secrets` about 2.0 KB and the total about 8.7 KB, so AWS would refuse the cloud grant write or the device's reported update. Hence the positional slot form, `max` dropped (constant 16, still returned by REST) and only a 0/1 MAC flag in the shadow; the MAC itself is returned by `GET /api/v1/secrets`. `kid` stays in full because the tool selects the certificate by it. The margin is small, so e2e task 7.6 measures the real document with read-only `GetThingShadow` on dev with a maximal grant list reported and pending in desired, 16 maximal secrets, 16 `tunnel_ports` and an active tunnel. If it exceeds 8192 B, this design is revised before merge (next lever: report a 16-hex `kid` prefix and let the tool match by prefix). Task 7.6 extends add-gateway-modules task 5.3, which measures grants without slots.

### D9. Dev NVS browser: namespace-level opacity
Key-name matching would not catch `s00`. The browser redacts every entry of `secrets_ns` and refuses raw writes there, since a raw blob write would bypass name, target and value validation and desync the RAM cache.

### D10. Operator tool
`source/utils/gateway_secret.py`, sibling of `shadow_cli.py`, boto3 already a dependency, `cryptography` added with `uv add`. Read-only calls for discovery (`iot:ListThingPrincipals`, `iot:DescribeCertificate`, `iot-data:GetThingShadow` for `kid` and `hwm`); `--mac` optional, taken by the operator from `net_scan`, with a warning when absent; `iot-jobs-data:StartCommandExecution` with the existing `energyme-<product>-<env>-gateway` template to dispatch, prod guarded by an explicit confirmation like the lan_tunnel tool. Golden vectors with and without a MAC (test-only RSA key pair committed under `source/utils/tests/fixtures/`, clearly named test-only, never a device key) are shared between pytest and the bench decrypt check.

## Risks / Trade-offs

- [`command_events` keeps every envelope forever; a later leak of a device key decrypts its history] → Envelopes for a device are only useful with that device's key, which leaks only with physical access, which also yields the plaintext slots. Rotate the LAN credential after a device is lost.
- [Local REST `PUT` sends the value over plain HTTP on the LAN] → Same exposure as using the equipment's own HTTP UI on that LAN; digest auth keeps out unauthenticated writers. AsyncWebServer body buffers cannot be zeroized; they are freed right after the request.
- [RSA OAEP-SHA256 or the stack budget fails on the device] → Task 1 measures before any store code. Fallback A: if `PKCS1_V21` with SHA-256 cannot be made to work, envelope `alg` `RSA-OAEP+A256GCM` (OAEP with SHA-1, still IND-CCA2) with the same AAD and `v: 1`, recorded here. Fallback B: if gateway stack high-water during decrypt leaves under 1.5 KB free, raise `GATEWAY_TASK_STACK_SIZE` (internal RAM, measured cost) rather than moving the op to another task.
- [A legitimate NIC or controller replacement changes the MAC] → every request using that secret stops with `TARGET_MAC_CHANGED` until the secret is set again with the new MAC; failing closed is the intent, as for grants.
- [Full `system` shadow close to 8 KB] → positional slot form (D8) and the measured worst case in task 7.6.
- [Short or common values cause scrub false positives] → 4-byte floor; scrub only on results of requests that expanded a secret.
- [Scrub replacements make a reply longer than its buffer] → the output is bounded by the buffer cap and cut there with `truncated` (D7), so a reply full of short echoes loses its tail instead of overflowing PSRAM or the published cap.
- [Collision on `issued_at` between concurrent operators] → One automatic retry in the tool; rare in practice.
- [Crash during expansion leaves the value in a core dump] → Zeroize narrows the window; core dumps stay on the device unless explicitly fetched.
- [NVS partition full] → `NVS_WRITE_FAILED` distinct from `SECRET_STORE_FULL`; init logs free entries at DEBUG.

## Migration Plan

New namespace, no data migration. Firmware without this change rejects the ops with `UNKNOWN_OP`, so the tool needs no version check. After rollout, rotate the XWEB password on the XWEB, store it with `gateway_secret.py set --mac <xweb mac>` (MAC from `net_scan`), and switch the XWEB commands to `${secret:xweb_admin|url}`. Rollback to older firmware leaves `secrets_ns` in NVS unused. Older firmware does not list it as excluded, so its factory reset clears it, but its configuration backup would export the slots as blobs: delete all secrets (`gateway_secret.py delete`) before a `firmware_rollback` to a pre-secrets build.

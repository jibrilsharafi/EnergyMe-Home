## Context

See `proposal.md` - Why. Key facts that shape this design, gathered during exploration and a first (SAG-based) implementation attempt:

- The ISR → semaphore → line-cycle-cadence task → `_handleInterrupt()` status demux already exists and is proven in production (built for the grid-frequency EMA feature). ZXTO just needs to become another serviced bit in that same demux.
- `IRQSTATA_ZXTO_BIT` (14), `ZXTOUT_16` (0x100, default 0xFFFF) are already defined in the codebase; nothing new needed in `ade7953registers.h`.
- Datasheet mechanics (ADE7953 Rev. C, "Zero-Crossing Timeout"/"Zero-Crossing Detection"/"Zero-Crossing Interrupts", pp.43-45): `ZXTOUT` is a 16-bit countdown, decremented 1 LSB every 1/14kHz (~0.07ms resolution, max ~4.58s). It reloads on the raw zero-crossing detector output (both edges, LPF1 output). Reaching 0 with no reload sets `ZXTO` (voltage channel) in `IRQSTATA`. Confirmed from the datasheet text directly: the `ZX_EDGE` config bits (which restrict `ZXV`/`ZXIA`/`ZXIB` to only positive- or negative-going edges) explicitly do **not** affect `ZXTOUT`'s reload - "changing the ZX_EDGE bits affects only the ZX status bits and interrupts." So the normal (healthy-line) reload interval is one half line cycle (~10ms @ 50Hz), not gated by our `ZX_EDGE` configuration.
- A fixed internal zero-crossing threshold (1250:1 of full scale) means `ZXTO` keeps functioning correctly even at very low input - it doesn't depend on catching a clean edge near a vanishing signal.
- First attempt used SAG (`SAGCYC`/`SAGLVL`, `IRQSTATA` bit 19) as the trigger. Bench-tested via a real plug pull / switch; produced no observable log entry at all, neither serial nor UDP. Root cause not conclusively isolated (could be the primitive, the pipeline timing, or the test itself), but rather than keep debugging blind, the decision was to switch primitives entirely and remove SAG's code so the next bench round is a clean, unconfounded observation of ZXTO. See "Decisions" below for the SAG-vs-ZXTO tradeoff analysis that was already done up front (and still holds as context for *why* ZXTO is a reasonable substitute, not just a guess).
- Physical hold-up budget (v6.1 hardware, 3300µF external cap, ~100mA load): roughly 10-26ms depending on allowed droop before regulation/BOD margin gets uncomfortable, plus an unquantified but likely modest bonus from the PSU's own internal reservoir. This budget is *not* the concern of this change (no MQTT/publish work here) but it's why the trigger has to be as fast as the hardware allows - anything slower eats directly into a budget that's already thin.
- The bench device available for testing (`esp32s3-dev-v5` build environment) is a different hardware revision (smaller cap, non-isolated voltage sensing) than the v6.1 board the hold-up budget above was computed for. It validates ADE7953-level detection behavior; it does not validate v6.1 hold-up timing.
- Verified from actual code (`_handleInterrupt()`): the original "unhandled interrupt" check was `(statusA & handledIrqMask) == 0` - true only when *no* recognized bit is present. A ZXTO (or SAG) bit co-occurring with ZXV (which fires every line cycle) would never trip this check, so arming either without also fixing this check produces zero observable signal anywhere. Further hardened: `IRQSTATA` reports every channel/energy event continuously regardless of `IRQENA` (enable only gates the physical IRQ pin, not the status bit), so the check is now restricted to bits actually enabled in `IRQENA` - otherwise routine current-channel/energy noise (e.g. `WSMP`, `ZXTO_IA`) floods the same warning.
- Verified `LOG_FATAL` usage elsewhere: it is a severity marker plus a `statistics.logFatal` counter only. It never triggers a reboot or crash-dump archive by itself. Safe to use here with no hidden side effects.
- Verified `AdvancedLogger`'s queue behavior: once the log queue saturates, the *producer* drains an entry inline (`Serial.println` + LittleFS `_save()` + forced `flush()` on FATAL + periodic whole-file rewrite). Sustained high-rate FATAL logging therefore pushes synchronous flash writes onto whichever task is producing them - here, the priority-5 meter-reading task - stalling ZXV/CYCEND servicing. This is why a runaway-firing guard is a correctness concern, not just tidiness.

**Phase 1 bench-validated (2026-08-09):** ZXTO fired correctly on a real plug-pull, a burst of `LOG_FATAL` entries reached AWS via the existing log-forwarding pipeline, and the device's next boot showed `lastResetReasonString: "Power on"` with an uptime placing the reset a few seconds after the burst - the alert reached the cloud before the device actually lost power. This validated the primitive and pipeline; phase 2 below is about the cloud alarm itself.

**Phase 2: two failed rounds with `IssueRegistry`, before moving to a direct publish.** The first attempt wired a `grid_voltage_loss` code through the existing issue registry (evaluated in `_evaluateGlobalCodes()`, raised via the normal 4-state lifecycle, surfaced through the `issues` shadow). Both the registry task and the MQTT task were, at the time, only ever woken by `ulTaskNotifyTake(pdTRUE, ticks)` - a poll-only wait with no way for another task to wake either one early, so a raised issue could sit for up to `ISSUE_REGISTRY_TICK_INTERVAL` (5s) before the registry even noticed it, then up to `MQTT_LOOP_INTERVAL` (100ms) more before the MQTT task noticed the resulting shadow-report flag. Two bench tests confirmed the AWS shadow never updated in time (or at all) even after fixing that: `xTaskNotifyWait`-based bit notifications were added to both tasks (`IssueRegistry::requestImmediateEvaluation()`, `Mqtt::requestImmediatePublish()`, both layered on a new shared `TASK_NOTIFY_SHUTDOWN_BIT` convention so `stopTaskGracefully()` kept working unchanged for every other task using it), closing the poll-interval latency at every hop - and the shadow still didn't make it out in a bench window (~1.7-2.6s) comparable to the one that worked fine for the plain log-forwarding pipeline in phase 1. The remaining difference was the *shape* of the publish itself: the shadow path builds the full reported-state doc (`issuesToJson()` walking all 32 issue-instance slots) via `Shadow::checkPublish()`, which also runs a drift check across every other writable shadow - meaningfully heavier than the flat, few-hundred-byte JSON object the log-forwarding pipeline was already sending successfully. Conclusion: the registry's generic path just wasn't a fit for a payload racing a hardware deadline, independent of wake latency.
- **Fix applied:** publish a minimal, dedicated alarm payload directly from `Ade7953::_handleZxtoInterrupt()` (`Mqtt::pushAlarm()` - a `FreeRTOS`-queue producer, same cross-task-safe pattern as `pushLog`/`pushMeter`/`pushGrid`), to its own MQTT topic/AWS IoT Rule, checked first in `_handleConnectedState()` ahead of the log queue and everything else. `grid_voltage_loss` was removed from `IssueLogic::Code` and the registry entirely - it is not an issue-registry-tracked state; the alarm is the only cloud surface for this signal.
- The two `xTaskNotifyWait` wake mechanisms built along the way (`requestImmediateEvaluation()`, `requestImmediatePublish()`) were kept: they're still a real, generically-useful latency fix for the registry's/MQTT task's *own* normal traffic (issues, shadow reports, channel-config pushes, etc.), just not sufficient on their own for this one deadline-critical alarm.

## Goals / Non-Goals

**Goals:**
- Get a grid-loss interrupt reliably firing and observable (log + counter) on real hardware, fast enough to matter given the hold-up budget.
- Fix the interrupt demux's "unhandled bit" blind spot generally, not just work around it for one trigger.
- Bound the worst-case cost of a misconfigured or sustained-runaway trigger condition without losing the ability to fully observe a real, brief event for bench validation.

**Non-Goals:**
- `ZXTOUT` becoming user-configurable (REST/shadow-exposed). Fixed constant for this first pass.
- Persisting grid-loss events across reboots (NVS). A bench unit tested via plug/switch (not full destructive outage every time) can observe the log live; a device that actually browns out loses ADE7953 register state and current-boot log buffer anyway, so reboot-persisted history is a separate, later concern if it turns out to matter.
- Debounce/hysteresis logic beyond the suppression window (see Decisions) to suppress legitimate brief dips that aren't blackouts. The point of this phase is to observe real firing frequency, not pre-guess it.
- Re-adding SAG as a second, independent trigger. A candidate for later, once ZXTO's real-world behavior is characterized - not mixed into this pass.
- Tracking grid-loss as an `IssueRegistry` state (`/issues`, device shadow) - tried, found too slow for this alarm's deadline (see Context), removed. The direct alarm topic is the sole cloud surface.
- Task-priority changes or `PubSubClient` concurrency work beyond the existing single-owner-task (MQTT task) model - `pushAlarm()` stays within that model, same as every other cross-task MQTT producer.

## Decisions

**ZXTO (not SAG) as the trigger primitive - reversed from the initial decision.** The original tradeoff analysis: `SAG`'s below-threshold comparison catches a declining-but-not-yet-absent waveform, which `ZXTO` (complete absence only) cannot; `ZXTO` in turn has a lower false-positive rate on non-blackout dips (motor inrush etc.) since it only fires on a genuine dropout. That analysis still holds as a description of the tradeoff - but SAG produced zero observable output on a real bench test, for a cause not yet isolated. Given the physical chain (the ADE7953 senses AC mains upstream of the PSU/bulk cap, so a real blackout collapses that signal toward zero almost immediately), a genuine blackout is expected to be a "complete absence" event in practice, not a lingering partial sag - so ZXTO should catch the case that actually matters here, and is not expected to be meaningfully slower: sized to ~15ms (see below), it's in the same ballpark as SAG's own achievable minimum. SAG's code is removed rather than kept alongside ZXTO so the next bench round is a clean read on whether ZXTO alone succeeds where SAG did not - re-introducing SAG as a confirmation signal is left as a candidate for a later phase, not mixed into this pivot.

**`ZXTOUT` sized to ~15ms ("miss one cycle"), fixed, not configurable.** Confirmed from the datasheet that `ZXTOUT` reloads on the raw zero-crossing detector output (both edges), independent of the `ZX_EDGE` config - so the normal healthy reload interval is one half line cycle (~10ms @ 50Hz), not a full cycle. The safe minimum has to clear the worst-case healthy gap: half-cycle at the low end of normal grid frequency tolerance (~10.6ms @ 47Hz) plus margin for LPF1's own ~2.2ms phase delay. ~15ms clears that with a small margin while still firing on a single missed crossing. This is a fixed absolute duration (unlike `SAGCYC`, which is a self-adapting cycle count), so it's less tunable to the actual measured line frequency - flagged as a starting point, not a verified-optimal number; tune from bench data like SAG's constants were meant to be.

**`LOG_FATAL` for the trigger, no new logging path.** Matches existing convention exactly (see Context) and needs no new infrastructure. It is deliberately *not* wired to trigger any reboot/recovery action - this phase is observation only.

**Fix the demux "unhandled" check generally, not with a trigger-specific carve-out, and restrict it to enabled bits.** The bug (any bit outside the handled set is silently dropped whenever a handled bit co-occurs) is generic, not trigger-specific. Further: `IRQSTATA` reports every channel/energy event continuously regardless of `IRQENA`, so restricting the check to `statusA & DEFAULT_IRQENA_REGISTER` before comparing against the handled set means only a genuine future misconfiguration (an enabled-but-unhandled bit) can ever trip the warning - routine current-channel/energy noise is excluded categorically, not bit-by-bit as it's discovered.

**New statistics counter, mirroring existing pattern.** `ade7953ZxInterrupts` / `ade7953UnhandledInterrupts` already exist; `ade7953ZxtoInterrupts` replaces the removed `ade7953SagInterrupts` for `/system/info` visibility, consistent with how the codebase already surfaces this class of counter.

**Flat 60s suppression window against runaway firing - replaces the phase-1 `CYCEND`-rearmed burst latch.** `ZXTO` has no hardware debounce beyond its own timeout window, so a misconfigured `ZXTOUT` or a sustained no-AC condition (board stays powered from elsewhere, e.g. a bench unit on USB with AC disconnected) can re-fire roughly every `ZXTOUT` period indefinitely. The phase-1 design (`_zxtoBurstCount`/`_zxtoSeenThisCycendWindow`: log the first 3 in full, one suppression notice, then count-only until a clean `CYCEND` window) worked, but bench testing under phase 2 showed each of those extra FATAL logs and their MQTT log-forwarding was directly competing for the same thin MQTT-task window the alarm itself needs - not just a flash-write/logging concern anymore, a latency concern for the deadline-critical path. Simplified to a single `uint64_t _zxtoLastTriggerMs` timestamp: only the first ZXTO since `ADE7953_ZXTO_SUPPRESS_MS` (60s) ago does anything beyond counting (alarm push + FATAL log); every other occurrence in that window is `LOG_DEBUG`-only, which `pushLog()` filters out before it ever reaches the MQTT log queue (below the default MQTT log level), so a runaway condition costs nothing on the MQTT task at all beyond the one real trigger. Dropped the `CYCEND`-based early rearm entirely - a flat time floor is simpler and "one alarm per minute, worst case" is an acceptable ceiling for a condition that, if real, ends in a device reset anyway.
- This does not lose observability: `statistics.ade7953ZxtoInterrupts` still counts every single occurrence untouched, and suppressed occurrences still get a `LOG_DEBUG` line (visible locally/UDP) - only the FATAL/alarm/registry-adjacent work is throttled.

**Alarm published directly from `ade7953.cpp`, not routed through `IssueRegistry` or `Shadow`.** See Context for the two failed rounds that led here. `Mqtt::pushAlarm()` is a plain `FreeRTOS`-queue producer (`AlarmEntry`, mirrors `LogEntry`/`PayloadMeter`) - safe to call from any task including the ADE7953 meter-reading task, same contract as `pushLog`/`pushMeter`/`pushGrid`. It is *not* safe to call anything that touches `PubSubClient` (`_clientMqtt`) directly from a non-MQTT task; `Shadow`'s own direct `Mqtt::publishReservedThings()` call is safe only because `Shadow` has no task of its own - every one of its publish-touching functions runs synchronously on the MQTT task's own call stack (via `Shadow::checkPublish()`, called from `mqtt.cpp`'s `_handleConnectedState()`). `pushAlarm()` respects that same boundary: it queues data and wakes the MQTT task (`requestImmediatePublish()`); only `_publishAlarm()` (running on the MQTT task) ever touches the client, via the same `_publishJsonStreaming()` primitive `Shadow` uses.
- New dedicated MQTT topic/AWS IoT Rule (`MQTT_TOPIC_ALARM "alarm"`, `AWS_IOT_CORE_RULE_ALARM`), following the existing one-rule-per-category convention (`meter`/`grid`/`energy`/`log` each already have their own) rather than reusing the log rule, whose SQL/downstream shape is unknown from this repo and not safe to assume compatible with an alarm-shaped payload.
- `_processAlarmQueue()` drains first in `_handleConnectedState()`, ahead of `_processLogQueue()` and everything else, so a queued alarm is never stuck behind a backlog of routine log lines.
- The payload is deliberately minimal (code, channel, severity, message, timestamp) and independent of `IssueLogic`/`IssueRegistry` - no shared enum, no catalog lookup, no issue-instance lifecycle. An alarm is a direct, fire-and-forget MQTT message, not a tracked state.

**Shared `TASK_NOTIFY_SHUTDOWN_BIT` convention (`constants.h`), `stopTaskGracefully()` migrated to it.** Needed once any task wanted to distinguish "woken for a specific reason" from "woken to shut down" via `xTaskNotifyWait` instead of the codebase's previous `ulTaskNotifyTake`-only idiom. `stopTaskGracefully()` now signals via `xTaskNotify(handle, TASK_NOTIFY_SHUTDOWN_BIT, eSetBits)` instead of a plain `xTaskNotifyGive()` (unconditional increment) - every existing `ulTaskNotifyTake(pdTRUE, ticks) > 0` consumer across the codebase is unaffected, since none of them read anything but the truthiness of the returned value. `IssueRegistry::requestImmediateEvaluation()` and `Mqtt::requestImmediatePublish()` both layer their own bit on top of this shared one. Kept as a lightweight shared bit-position convention only, not a generic wrapper function - see the exploratory discussion during this change: with only two real consumers so far, a shared "wait and dispatch" helper would be guessing at a shape from insufficient evidence (`customwifi.cpp` independently arrived at an equivalent bit-0-for-shutdown pattern before this convention existed, which is corroborating evidence for the convention, not yet for a shared helper function).

## Risks / Trade-offs

- **[Risk]** `ZXTOUT` at ~15ms may still false-trigger on frequency wobble or LPF1 jitter not fully characterized ahead of real bench data → **Mitigation**: explicitly the point of this phase - observe real firing frequency from logs/counter; the value is documented as a tunable starting point, not a verified-final one.
- **[Risk]** Root cause of SAG's silent bench failure is not conclusively known, so it's possible ZXTO hits the same underlying issue (e.g. a pipeline/logging timing problem rather than a primitive problem) → **Mitigation**: none within this change beyond switching primitives and re-testing; if ZXTO also produces nothing, the next investigation should look at the ISR→task→log pipeline itself rather than the primitive.
- **[Risk]** The available bench hardware (`esp32s3-dev-v5`) has a different hold-up profile (smaller cap, non-isolated design) than the v6.1 board this was scoped for → **Mitigation**: this phase validates ADE7953-level detection behavior and firmware correctness only; timing/hold-up conclusions from this bench unit do not transfer to v6.1 survival estimates, and that distinction should be called out explicitly whenever results are discussed.
- **[Risk]** Loosening the "unhandled interrupt" check could surface previously-silent warnings for other latent conditions → **Mitigation**: restricted to bits actually enabled in `IRQENA` (ZXV/ZXTO/CYCEND/RESET/CRC), so any other bit appearing there would itself be a genuine, previously-undetected misconfiguration worth seeing - this is the intended effect of the fix, not a side effect to guard against.

## Migration Plan

- Branch off `development` (per project convention), Conventional Commits, one concern per commit.
- Build/flash via the `esp32s3-dev-v5` PlatformIO environment (matches the bench device on hand).
- Bench validation: induce a grid-loss event via plug pull or switch on the bench device; confirm `LOG_FATAL` entry appears (serial/UDP log listener) and, on any run where the device survives to observe it, the `ade7953ZxtoInterrupts` counter via `/system/info`; confirm the alarm topic is received on the AWS side (the device-side publish succeeding is not sufficient proof - see Context, phase 2).
- `AWS_IOT_CORE_RULE_ALARM` provisioned server-side (infra repo) - confirmed done.
- No persisted state introduced (`ZXTOUT` is a volatile ADE7953 register, rewritten every boot in `_setupInterrupts()`) - rollback is a plain revert with no migration/backward-compat concern.

## Open Questions

- Exact `ZXTOUT` value (~15ms starting point) - tune from real bench data; doesn't change the approach or task breakdown.
- Whether the SAG-vs-ZXTO bench failure was actually the primitive, or a pipeline/timing/logging issue that would affect either - only resolvable with a real ZXTO bench test (resolved in practice: ZXTO's own detection/logging worked from the first bench test; the later cloud-delivery issue was unrelated, in the shadow publish path, not the primitive).
- Whether ZXTO events should eventually persist across reboots (NVS) for post-mortem inspection after a real brownout-triggered reboot - deferred; doesn't block this phase's log-based bench validation.
- Whether SAG should be reintroduced later as a confirmation signal alongside ZXTO - deferred to a future phase, informed by ZXTO's own bench results.
- Whether the alarm actually reaches AWS within the capacitor hold-up window on this bench hardware - not yet confirmed; the direct-publish redesign removes the shadow-path bottleneck identified in two prior rounds, but a clean end-to-end bench confirmation (device log shows the alarm published, AWS side confirms receipt, before/without a reset in between) is still outstanding.

## Why

LAN equipment data (first the Dixell XWEB refrigeration supervisor at site IT000010, then Modbus TCP meters, HTTP APIs, Shelly) can today only be read by the cloud sending one-shot `gateway` commands: one execution slot shared with support work (`GATEWAY_BUSY`), a 4 KB reply cap, an IoT command plus a `command_events` row per poll, nothing collected while the cloud is unreachable, and credentials in command parameters. ADR-034 (infra) decides that the meter acquires raw replies on a schedule and the cloud decodes them; this change is the device half of that decision.

## What Changes

- New `collector`: scheduled polling jobs that run on the device, on top of the `add-gateway-modules` executor and the `add-gateway-secrets` store. The device polls, captures session tokens and publishes raw replies. It never decodes vendor formats and has no loops or conditionals.
- New seventh named shadow `collector` (writable). `desired` carries an `enabled` switch and a `jobset` object with `rev`, `sha256` and the job document as one JSON string, so the delta stays inside the 9 KB inbound MQTT buffer and the 8 KB shadow limit (a structured list would add per-leaf metadata to the delta). `reported` carries the applied revision and hash, an apply error and per-job health, never a copy of the jobs. `SHADOW_MAX_COUNT` goes from 6 to 7.
- Jobs persist on LittleFS and keep running without the cloud. Per job: target, module, interval (>= 60 s), jitter, step timeout, run deadline, `max_bytes`, session (login steps, captures, expiry rule, TTL, re-login once), up to 8 steps, vars (`clock_offset_s`, `overlap_s`, `backfill_s`, `window_max_s`, free vars) and publish mode. Placeholders `${now}`, `${cursor}`, `${var:x}`, `${cap:x}` passed per call to the expansion stage of `add-gateway-modules` and resolvable only inside a job run, `${secret:x}` from `add-gateway-secrets`. Replies of steps that expanded a secret are echo-scrubbed by the executor (`add-gateway-secrets`, flagged `redacted`), replies of steps that expanded a capture by the collector, and the part header carries one `rd` flag for both.
- Quotas: 8 jobs, 8 steps plus 4 login steps per job, 8 captures, 8 vars, job document <= 5120 bytes, hourly byte budget, 256 KB PSRAM out-queue that drops oldest with counters. Jobs are read-only as far as the device can tell: steps are classed against the stored read declarations of `add-gateway-modules` (exact `<METHOD> <path>` addresses for non-GET HTTP, exact raw payload hashes, MAC-bound on-link), never a per-step flag; a step classed write is refused at apply time, every step is classed again at run time under `writes: "deny"`, and write grants never apply to jobs. Residual: a GET step is read by method, so a state-changing GET is not caught on the device; the control is the infra jobs tool, which accepts a GET step only when it matches the driver's `READ_REQUESTS`.
- Clock and robustness rules: jobs with time placeholders wait for NTP, cursor plus overlapping window advanced only after publish, capped window length (backlogs caught up one window per run, halved after a truncated reply), per-job backoff, dedup key `(boot, job, seq, step, chunk)` plus body SHA-256, pause during tunnel sessions, OTA and low heap.
- Scheduler runs inside the existing gateway task between queue polls (no new task stack). **BREAKING (spec only)**: a cloud `gateway` command that arrives while a collector run is active waits at most one step instead of being rejected with `GATEWAY_BUSY`. `GATEWAY_BUSY` stays for a second command while one command is queued or running.
- Raw publish on `$aws/rules/<AWS_IOT_CORE_RULE_COLLECTOR_HOME|_HOMEPRO>/energyme/<product>/v1/<device_id>/collector/<source_id>`: binary payload of one or more parts, each a one-line JSON header plus raw bytes. Results above 48 KB are chunked; small results for the same source are coalesced up to 5 KB (the IoT billing unit).
- New `gateway` op `collector_status` (on-demand health, answered by the MQTT task, no gateway slot).
- Collector switch `collector_enabled`, default off, in NVS, the `collector` shadow and `GET/PUT /api/v1/collector`. It is its own switch, separate from `gateway_enabled`, and the collector runs only while both are on (`gateway_enabled` stays the master switch for all LAN traffic, as for the tunnel).

## Capabilities

### New Capabilities
- `lan-collector`: job set delivery through the `collector` shadow and its size budget, persistence, job schema, placeholders and captures, session handling, scheduling, cursor and clock rules, quotas, priority and pausing, raw publish format and topic, out-queue, switches, health and `collector_status`.

### Modified Capabilities
- `lan-gateway`: the "Gateway work never blocks the MQTT task" requirement changes `GATEWAY_BUSY` semantics (commands wait at most one collector step); `collector_status` is added as a gateway op through an ADDED requirement, so the contested "Gateway command envelope" requirement is not modified here.
- `iot-device-shadows`: seven named shadows instead of six, `collector` writable.

## Dependencies

- Depends on `add-gateway-modules` (executor, structured result with header block, `max_bytes`, read/write classing with read declarations, `writes: "deny"` read-only caller field, template expansion stage with its per-call `Resolver*`) and on `add-gateway-secrets` (`${secret:x}` bound to the job target). Both must be implemented first; archive order: `add-lan-tunnel`, `add-gateway-modules`, `add-gateway-secrets`, then this change.
- Cross-repo: infra ADR-034 (identity and raw-acquisition decisions) and infra change `energyme-home-iot-pipeline-lan-points`, which must deploy the Basic Ingest rules `energyme_{home,homepro}_{env}_rule_collector`, add `collector` to `KNOWN_SHADOWS`, write the read declarations a job set needs into `system` desired `gateway_write_grants` (acked) before the job set, and keep the authoritative job set per device (the device nulls `desired` on apply, as for every writable shadow).

## Impact

- Firmware: new `source/lib/collector_logic/` (pure: job schema validation, template inputs, capture extraction, scheduling, backoff, window, header encoding, coalescing, budget; Unity-tested), new `source/src/collector.cpp` + `source/include/collector.h`, `gateway.cpp` (scheduler in the task loop, command preemption between steps), `mqtt.cpp` (topic, out-queue drain, drain order, `collector_status`), `awsconfig.h` (`AWS_IOT_CORE_RULE_COLLECTOR_HOME` / `_HOMEPRO`), `mqtt.h` (`MQTT_TOPIC_COLLECTOR`), `shadow.cpp` (seventh shadow), `customserver.cpp` (`/api/v1/collector`), `utils.cpp` (factory reset), `swagger.yaml`.
- Memory: no new task stack; under 1 KB internal RAM for collector state plus the health snapshot, and up to +2 KB on the MQTT task stack only if the bench stack gate (task 4.2) needs it; job table, captures, out-queue (256 KB, allocated at boot when the collector is persisted on, else at enable, with a 60 s retry and per-job `NO_MEMORY` on failure) and one per-step body buffer of exactly `max_bytes` (gateway-modules D5) with chunked decoding during receive, in PSRAM; LittleFS one file of at most about 6 KB.
- Cloud (separate infra change): rule SQL must treat the payload as binary (not `SELECT *` JSON); the rule and the device policy must exist before any device enables the collector. The device policy already allows `$aws/rules/<prefix>*/...` publishes (energyme-home-registry and energyme-homepro-registry `iot_resources.py`).
- Cost: at most the configured hourly budget per device (default 2 MiB/h), billed in 5 KB units.

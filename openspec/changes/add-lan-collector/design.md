## Context

See proposal.md for the motivation. This change is the device half of infra ADR-034 and sits on two sibling changes: `add-gateway-modules` (executor, modules, structured result, read/write classing, template expansion with a per-call `Resolver*`, write grants for one-shot commands) and `add-gateway-secrets` (`${secret:x}` bound to a target). Constraints from today's code:

- Gateway task: one 8 KB internal stack (`source/include/gateway.h:23`), a depth-1 queue (`source/src/gateway.cpp:1013`), a loop that blocks up to `GATEWAY_QUEUE_WAIT_MS` = 1000 ms on it (`gateway.cpp:988`, `gateway.h:30`), and the `_busy` CAS that returns `GATEWAY_BUSY` (`gateway.cpp:41`, `gateway.cpp:1088`). The task is created at boot whatever `gateway_enabled` says (`gateway.cpp:1018`).
- MQTT: a 9 KB inbound buffer (`source/include/mqtt.h:84`, set at `source/src/mqtt.cpp:365`); bigger inbound packets are dropped by PubSubClient. Outbound bulk goes through `beginPublish` streaming (`mqtt.cpp:3229`), limited by the 16-bit remaining length to about 64 KiB. Only the MQTT task publishes. Rule topics are built by `_constructMqttTopicWithRule` (`mqtt.cpp:1161`) as `$aws/rules/<rule>/energyme/<product>/v1/<id>/<suffix>`, as for the alarm topic (`mqtt.h:187`, `mqtt.cpp:1222`, rule names `awsconfig.h:34`, `:39`, `:45`, `:50`).
- MQTT loop drain order today (`mqtt.cpp:3587-3601`): alarm, log, live publishes, offline energy replay (`:3596`, 48 KB chunks, `mqtt.h:108`), shadows, command, gateway result, tunnel.
- Shadows: fixed table `SHADOW_MAX_COUNT 6` (`source/src/shadow.cpp:30`), registered at `shadow.cpp:126-131`. `_applyDelta` (`shadow.cpp:303-345`) runs in the MQTT task and nulls every top-level key it received. AWS adds a `metadata` entry per leaf to every delta and limits a named shadow to 8 KB of state.
- `resetCount` lives in `RTC_NOINIT` memory (`source/src/crashmonitor.cpp:66`) and is zeroed whenever the RTC magic word is lost (`crashmonitor.cpp:172-175`), i.e. on every power cycle. It cannot be a dedup key.
- MQTT task stack is 7 KB (`source/include/mqtt.h:30`, "Around 6 kB usage"); measured floors are 820 B free (archived `2026-08-13-firmware-rollback-command/tasks.md:35`) and 2.1 KB free in the tunnel soak (`add-lan-tunnel/tasks.md:31`). The deepest path today is `Shadow::checkPublish` -> `_applyDelta` -> `desc.apply`, which already holds the `inDoc` and `outDoc` frames (`shadow.cpp:303-345`). The 3 s drift check calls each writable shadow's report builder on the same task (`shadow.cpp:409-416`).
- Today's `_runHttp` allocates a raw buffer (`gateway.cpp:415`) and a second 128 KB buffer for chunked decoding (`gateway.cpp:458`).
- mbedTLS allocates from PSRAM (`source/src/main.cpp:120`). HTTPS feasibility is gated in `add-gateway-modules`, not assumed here.
- Factory reset clears every non-excluded NVS namespace (`source/src/utils.cpp:1147`, which includes `gateway_ns`, `source/include/constants.h:98`) and formats LittleFS (`utils.cpp:1173-1182`).
- The tunnel already sets heap thresholds (`source/include/tunnel.h:44-46`: open at 45 KB free, close below 30 KB). The OTA busy check is `_otaTaskHandle != nullptr || _otaRebootPending` (`mqtt.cpp:1609`).

## Goals / Non-Goals

**Goals:**
- Poll LAN sources on a schedule, without the cloud, inside the existing gateway task and memory budget.
- Ship raw bytes with enough context (`job`, `rev`, `step`, window, dedup id, hash) for the cloud to decode, dedup and re-decode from S3.
- Keep cloud support commands responsive (wait at most one step) and keep live telemetry first.

**Non-Goals:**
- Any vendor parsing, loops, conditionals or scripting on the device.
- Control. Jobs are read-only, classed by the read declarations of `add-gateway-modules`; writes stay one-shot commands under its write grants. Local control rules are a later change (ADR-035).
- Persisting collected data across reboots. Sources with history (XWEB) backfill through the window; snapshot sources lose what was queued at reboot.
- Web UI. Local REST is an emergency switch and a status read.

## Decisions

### D1. Job set as one string leaf in the `collector` shadow

`desired = {enabled, jobset: {rev, sha256, doc}}` with `doc` the job document as a JSON string. A structured job list would make AWS put a `metadata` timestamp object on every leaf of the delta, roughly doubling it, and a 5 KB list would pass 9 KB and be dropped by PubSubClient with no trace. As one string, the delta metadata is four leaves (`enabled`, `rev`, `sha256`, `doc`). Budget: cloud-written `desired` <= 5632 bytes, device `reported` <= 2048 bytes (state total under 8 KB); the delta is then at most about 5632 + 400 (envelope, metadata, clientToken) + 70 (topic) bytes, leaving more than 3 KB of headroom under 9 KB. JSON escaping makes the stored string about 10-20% larger than the raw document; the cloud checks the serialized size, the device checks raw `doc` <= 5120 as a backstop.

Reported never has a `jobset` key, so a written `jobset` always produces a delta with the full object, and the device acks with `desired:{jobset:null}` (existing contract, `shadow.cpp:338-340`). The cloud keeps the authoritative job set (infra `energyme-home-iot-pipeline-lan-points`) and compares `reported.rev` and `reported.sha256`.

Reported health is an array, not a map. AWS merges nested objects key by key on update, replaces arrays whole and removes a key only when it is set to `null` (the firmware already relies on that, `tunnel.cpp:202`, `shadow.cpp:474`, `:494-496`). A map keyed by job id would keep a job that left the set, with its last `err`, forever, and a rebooted device no longer knows the old ids to null them; an optional `code` omitted on recovery would stay next to `st: ok`. So `reported.jobs` is `[{id, rev, st, since, code, detail}]`, always the whole array, every key present and `null` when empty, and `apply_error` always carries `{rev, code, job, field}` with `null` for the keys that do not apply. With 8 jobs at their maximum (32-character id, 10-digit rev, 22-character code, 24-character detail) and a full `apply_error`, the compact `reported` section is about 1530 bytes, inside the 2048-byte budget.

Too big, three tiers: above 8 KB AWS refuses the cloud write; under 8 KB but over 9 KB as a delta, the device never sees it and the cloud alarms when `reported.rev` lags for 10 connected minutes; parsed but invalid, the device refuses the whole set and reports `apply_error`. Splitting a job set across several shadow writes was rejected: partial sets would run, and atomicity would need a second protocol.

Alternatives: a `/get` on demand (the device never GETs, `iot-device-shadows`); jobs as IoT command payloads (no persistence semantics, each change a `command_events` row); base64 `doc` (fixed 33% overhead, worse than escaping).

### D2. Parse in the MQTT task, run in the gateway task

`_applyDelta` already runs in the MQTT task body with a PSRAM `JsonDocument`. The collector validates there into a compact PSRAM table of jobs (fixed-size structs plus string pool), so the gateway task's 8 KB stack never holds the job JSON. Validation logic (schema, quotas, template names, capture order, read/write classing via the `add-gateway-modules` classifier) lives in `source/lib/collector_logic` and is unit-tested on the host.

Handover. The gateway task owns the active table and all run state. The MQTT task posts the validated table to a one-slot mailbox (a newer post replaces and frees an unadopted one) and never waits. The gateway task adopts it only between steps, abandons the active run without advancing the cursor, migrates backoff, cursor, window length and session for jobs whose `id`, `rev` and binding are unchanged, zeroizes the rest and frees the old table itself. The binding is a per-job SHA-256 over the canonical serialization of `target`, `module` and `session`, computed by the MQTT task at apply and stored in the table. Captures have no target binding (D3), so trusting the cloud to bump `rev` whenever it changes a target would let a set that moves `target.ip` send the held XWEB `sses`, or a 1200-byte bearer token, to the new host on the next data step, as no login runs while a session is held. The device compares the hashes itself; a changed binding zeroizes the captures and the next run logs in first. The MQTT task's three readers (apply, drift report at `shadow.cpp:409-416`, `collector_status`) read a fixed-size snapshot struct (per job: state, code, since, counters, next run, cursor; about 100 B per job, under 1 KB) copied under a mutex held only for the `memcpy`. Rejected: one mutex over the table (either the MQTT task blocks for a whole step, up to 10 s plus a TLS handshake, stalling telemetry and keepalive, or the swap frees strings and captures under a running expansion).

MQTT stack. Applying a set adds a second nested `deserializeJson` (a 5120 B string up to 8 levels deep; ArduinoJson recurses per level), validation and a LittleFS write on top of the `_applyDelta` frames, on a task with under 1 KB measured headroom. Decision: keep the apply in `_applyDelta` (so the ack stays one message with `reported.rev`, `sha256`, `apply_error` and `desired:{jobset:null}`), keep validation iterative in `collector_logic` (no recursion over steps), and gate it on task 4.2: MQTT task high-water with at least 1 KB free while applying a synthetic 5120 B, maximally nested document, during `collector_status` and during a collector publish. If the gate fails, `MQTT_TASK_STACK_SIZE` (`mqtt.h:30`) grows by the measured shortfall rounded up to 1 KB, bounded at +2 KB (at most 2 KB less free internal heap, re-measured against the 40 KB pause threshold in task 4.2); a larger shortfall moves validation and persistence to a deferred step at the top of the MQTT loop, before the ack. `collector_status` builds its 3500 B result in a PSRAM buffer, never on the stack.

Persistence: `/collector/jobset.json.tmp`, fsync, rename to `/collector/jobset.json`, then ack. LittleFS rename is atomic, so a power cut leaves either set. A same-hash re-send with a higher `rev` is a no-op for the jobs but still rewrites the file with the new `rev` the same way before the ack. The jobs tool always writes `rev` = max + 1, so a rev held only in RAM would go back at every reboot, the part header `set` would regress with it and the cloud's 10-minute `reported.rev` lag alarm would fire after each reboot. `collector_enabled` is key `collector_en` in `gateway_ns`, so factory reset clears it; the LittleFS format clears the file.

### D3. Scheduler in the gateway task loop

The loop becomes: wait on the command queue for `min(1000 ms, time to next due job)`; if a command arrived, run it; else if a job is due and not paused, run one step of it and loop. A run is a small state machine (`login[i]`, `step[i]`, retry flag, captures, deadline) in gateway-task-owned run state beside the table (D2), so the task returns to the queue between steps and a command waits at most one step. The mailbox is checked at the same point, between steps. Time spent on a command is added to the run deadline. No new task, no new stack.

Resolvers. The engine takes a `Resolver*` per `expand()` call (gateway-modules design.md:84). The collector passes a chain `now`/`cursor`/`var`/`cap` bound to the running job, falling through to the secret resolver; the command adapter passes the secret resolver alone. So `${cap:x}` in a one-shot command is `BAD_TEMPLATE` with no socket, and a captured value, which has no target binding, can never be sent to another host or echoed into `command_events`.

Step outcomes. On a TCP-to-RTU gateway a dead slave gives a timeout, not exception 0x0B, so for `modbus_tcp` a `TIMEOUT`, `NO_REPLY` or `BAD_RESPONSE` is a per-unit result and the run continues, but only when the executor result has `connected` true. The reason code alone cannot say whether the connect completed, and `bytes_tx` is not used for this decision (a connect that completes and fails before sending would read as unreachable). A refused connect is `CONNECT_FAILED`, while a powered-off gateway that never answers the SYN uses up the step timeout and is coded `TIMEOUT` (`gateway.cpp:242-244`, kept for commands by the golden rule). With `connected` false the collector treats those codes as run-stopping, like `CONNECT_FAILED`, so an unreachable gateway does not run every step to its timeout until `deadline_s`. `connected` is the executor result field `add-gateway-modules` adds for exactly this purpose. A run fails for backoff and health only when it was stopped or no data step was `OK`; otherwise one silent meter would drop every healthy meter on that gateway to one poll per hour.

`GATEWAY_BUSY` now means only "a command is queued or running": the `_busy` flag covers commands, not collector work. The command result path (`takeResult` from the MQTT task) is unchanged.

Rejected: a second task (another internal stack of at least 8 KB on a heap that already carries TLS, the tunnel and the energy path); running whole runs atomically (an XWEB run with login is 2 steps of up to 8 s; a Modbus run of 8 units can be 8 s; that would bring back `GATEWAY_BUSY`).

### D4. Out-queue and drain in the MQTT task

The gateway task writes each part (header fields plus bytes) into a 256 KB PSRAM ring under a mutex; on overflow it drops oldest whole bodies and counts. The parts the MQTT task is streaming are pinned: the MQTT task marks them in flight under the mutex, releases the mutex for the TLS write (never held across a 48 KB write), and drop-oldest skips pinned parts; if only pinned parts remain, the new part is dropped instead and counted the same way. The per-job quota (data `max_bytes` sum <= 131072, half the ring) keeps one run from evicting its own parts, which would otherwise stall a cursor job forever. The MQTT task gets a new `_serviceCollector()` after `_serviceTunnel()`, and `_checkOfflineEnergyReplay()` moves to after it, giving the order live publishes, shadows, command, gateway result, tunnel, collector, replay. `_serviceCollector()` publishes at most one message per pass and at most one per 1000 ms, independent of the loop cadence (100 ms, or 10 ms while a tunnel is open, `mqtt.h:129-130`), the same pace as the offline energy replay (`mqtt.h:107`, `mqtt.cpp:3039`). Without it a full 256 KB queue would go out as back-to-back 48 KB TLS writes. It publishes nothing while a tunnel session is open, while an OTA download or OTA reboot is pending (`mqtt.cpp:1609`), or while internal heap is under the D7 low-heap thresholds, since a concurrent TLS uplink during an OTA download is the known path to internal heap exhaustion on this device. Runs are paused in the same states (D7), so the queue does not grow meanwhile. Otherwise it takes the head part plus following parts of the same `source_id` while the message stays <= 5120 bytes, or a single chunk of a large body, and streams it with `beginPublish`/`write`/`endPublish` (header line, newline, bytes) from PSRAM without copying into the 9 KB buffer. It sets `ts` from `up` when the clock became valid since queueing. After `endPublish` succeeds it marks the parts published, which lets the job advance its cursor (D6). On a `beginPublish`/`write`/`endPublish` failure, a disconnect or a task restart it unpins them under the mutex and leaves them unpublished for the next connected pass, so a leaked pin can never wedge the head. A body whose first chunk is out is finished, or counted dropped whole (`dq`), never cut in the middle, so the cloud never holds a partial chunk set it cannot tell from a loss.

PSRAM budget per Home (2 MB): the 256 KB ring, allocated at boot when `collector_enabled` is persisted true (before PSRAM fragments), otherwise at the moment of enabling, and kept until reboot. An enable that comes days after boot can find no contiguous 256 KB block beside the tunnel pools, executor bodies and mbedTLS buffers. Then the switch stays on, no job runs, each enabled job reports `wait` / `NO_MEMORY` and the allocation is retried every 60 s, so the failure is visible in the shadow and recovers without a reboot; refusing the switch would hide it behind an `enabled: false` the operator never wrote. Beside the ring: per step one executor body of exactly `max_bytes` (gateway-modules D5) with chunked decoding during receive into that buffer, so the second 128 KB decode buffer of today's `_runHttp` (`gateway.cpp:458`) is gone; 2 KB headers; the job table (under 8 KB) and captures (at most 4 KB per job). Collector peak is therefore about 256 + 128 + 2 + 40 KB, beside the tunnel's 180 KB pools and mbedTLS. Fragmentation after hours of JSON alloc/free is unknown, so task 4.8 records PSRAM minimum free and largest free block, with a pass floor of a largest block of at least 2x the largest single collector allocation (2 x 131072 B). A 128 KB `NO_MEMORY` would otherwise fail every run as a transport failure. It does nothing while the tunnel is active (the collector is paused anyway, and the tunnel caps uplink at 25 frames/s).

Chunk size 49152 bytes matches the replay chunk size already proven on the device (`mqtt.h:108`) and stays under the 64 KiB `beginPublish` limit and the 128 KB AWS message limit with the header.

### D5. Part format: JSON header line plus raw bytes

A JSON header keeps the cloud side trivial (one `split(b"\n", 1)`, no binary schema) and stays readable in S3. The cap is 768 bytes: an `OK` https data part with every field at its maximum (32-character job and step ids, 64-byte `ct`, 40-byte `date`, `sha`, `win`) measures about 610 bytes, so the earlier 512-byte cap could not hold, and the cloud decoder accepts up to 1024 bytes. A part that is not `OK` carries `rc` and, when the executor gave a code-token reason_detail, `rdt` (at most 24 bytes; such parts have no `sha`, `ct` or `date` and stay under 500 bytes). `rdt` is what lets the cloud tell a revoked read declaration (`WRITES_DENIED`) from a swapped device (`TARGET_MAC_CHANGED`) or an on-link slot without a MAC (`MAC_REQUIRED`), which all share one `rc`. Multiple parts per message use `len` as the only framing. Raw HTTP header blocks are not published (they carry `Set-Cookie` and tokens); `ct` keeps what decoders need. Request bytes are never published (they may carry expanded secrets or session ids). Login replies publish status and length only (ADR-034).

Echo scrub, one owner per placeholder kind. Replies can echo request material (an error page listing request headers, a form echoing a field), and collector bodies are kept in S3 forever as the replay source. The executor already scrubs secrets for every caller, one-shot or collector step (`add-gateway-secrets` "Expanded secrets never leave the request" and its task 4.3), and reports it as `redacted` in `ExecResult`. The collector does not scrub secrets again, since a second pass would find no secret bytes left and lose the signal. It runs the same pure scrub function over the body the executor returned, for the `${cap:x}` values the step expanded and for every value the step captured from its own reply (raw form plus each encoding the job's templates apply to that capture), and ORs the executor's `redacted` into its own replacement flag. Covering the step's own captures matters for data steps: a continuation token, CSRF token or rotated session id taken from a body would otherwise be published in the very body it came from, although that step expanded nothing. Order: executor secret scrub (including the cut-prefix removal at `max_bytes`), then capture extraction, then the collector capture scrub (same cut rule), then `len`, `total` and `sha` over the final bytes, then chunking. Both passes keep the output within `max_bytes`, as `add-gateway-secrets` specifies for its scrub: when replacements would grow the body past the cap, it is cut at the cap with `tr: true`, leaving no partial value or partial placeholder at the cut. `rd: true` tells the decoder a placeholder replaced bytes, from either pass.

`date`. The decoder takes source timestamps as sent, with no offset (infra `energyme-home-iot-pipeline-lan-points` D7); data parts carry the raw `Date` value (at most 40 printable ASCII bytes) only for drift detection, which flags a source clock to fix at the source. It is the only header value that leaves the device and holds no session material; login parts never carry it.

The Basic Ingest rule cannot `SELECT *` a non-JSON payload; the infra change handles the payload as binary (`encode(*, 'base64')` into S3 or Firehose). That is the infra change's concern, listed here so the device format is not changed later to suit a JSON rule.

### D6. Time, cursor and dedup

- No source clock offset (ADR-0001, solve at the source): `${now}`, `${cursor}` and `win` are device UTC seconds and source timestamps are taken as sent. A source with a wrong clock, or a local-time clock across a DST change, is fixed at the source, preferably with NTP. A wrong source clock is silent on the device: windows come back empty with `st: "OK"` and the cursor advances past data the source still holds; only the cloud `date` drift check sees it. Adoption keeps a job's cursor and window length when its `id`, `rev` and binding are unchanged.
- The cursor is RAM only and advances on publish, not on run end, so a dropped part or a disconnect re-covers the window. After a reboot the backlog is `backfill_s`, initialised at the first run after NTP (cursor jobs never run before it). Persisting cursors would cost a flash write per run for no gain, since the cloud dedups overlap anyway.
- The window is capped at `window_max_s` and `${now}` is the window end, so a 6-hour backfill becomes six 1-hour requests on consecutive slots instead of one request that a `max_bytes` cut would turn into silent loss on a circular buffer. A truncated part in a cursor job fails the run (`TRUNCATED`) and halves the window, doubling back after each success: a size-adaptive rule with no vendor knowledge. The cost is catch-up time (6 runs at 300 s = 30 minutes for 6 hours of XWEB history), well inside the XWEB circular buffer depth.
- `boot` is a 16-hex random id per boot (`generateHexToken`, `source/include/utils.h:161`) instead of the reset count, which resets on power loss (Context). `seq` counts runs per job per boot.
- Jobs without time placeholders run before NTP; the MQTT task back-fills `ts` from uptime when the clock becomes valid before publish. If it is still invalid at publish, `ts` is `null` and the cloud uses ingest time with a clock quality flag.

### D7. Priority, pausing and budget

Live telemetry > commands and tunnel > collector > offline energy replay. Pauses: tunnel session, OTA download or reboot pending, internal heap below 40 KB free or 16 KB largest block (between the tunnel's open and close thresholds; the bench task confirms them). The same three states also stop the out-queue drain, which otherwise publishes at most one message per 1000 ms (D4). Jobs using `${cursor}` pause while the cloud is down, since the window will backfill; snapshot jobs keep queuing. The hourly token bucket (default 2 MiB/h, `budget_bytes_h` 64 KiB to 8 MiB) bounds IoT and S3 cost per device and protects the energy replay from starvation.

### D8. Switches

`collector_enabled` is a separate switch, and the collector also requires `gateway_enabled`, the same layering as `tunnel_enabled` in `add-lan-tunnel`. Collector jobs are cloud-defined LAN requests, so an independent switch would buy no safety and would break the one-call emergency stop (`PUT /api/v1/gateway`). The switch lives in the `collector` shadow (not `system`) so all collector state sits in one document. `collector_status` follows `GATEWAY_DISABLED` like every gateway op; while the gateway is off, health is still visible in the shadow.

### D9. Read-only jobs

Collector jobs never send a request the device classes write. The read/write class comes from stored configuration, never from the job: the `add-gateway-modules` classifier with the read declarations (`kind: "read"` entries of `gateway_write_grants`, exact canonical HTTP addresses `<METHOD> <path>` or exact payload SHA-256, MAC-bound for on-link targets). HTTP method alone is not the line (XWEB login and data queries are POSTs), so the XWEB needs one read declaration listing `POST /cgi-bin/login.lua` and `POST /cgi-bin/datachart.cgi`, stored before its job set. Another method to a declared path is write, and the body takes no part in the match, so an endpoint whose body selects the operation (Shelly Gen2 `POST /rpc`) is never declared read (gateway-modules D3). A per-step `access` flag was dropped: a step copied from the XWEB read steps to a setpoint CGI would keep the flag (gateway-modules D3), and the flag is set by the same cloud path that writes the job. Raw query protocols with fixed request frames (BACnet/IP ReadProperty, proprietary TCP queries) poll through payload-hash read declarations; a payload with a placeholder expands differently each run, never matches and is refused.

Two checks. At apply time every step is classed as written, so a set the device cannot run is refused whole (`WRITE_NOT_ALLOWED` with the step as field) instead of failing every interval. At run time the declarations may have changed (a grant list replaced, a device swapped behind the IP), so the collector sets `writes: "deny"` (gateway-modules "Read-only callers") on every step: a request classed write after expansion is `REJECTED WRITE_NOT_ALLOWED` / `WRITES_DENIED` before the grant check and before any socket opens, and the run stops. The job schema has no `writes` key. Write grants never apply to jobs: a grant issued for one-shot control can cover a whole tcp/udp target or a Shelly `["*"]`, so honouring it would replay the same bytes every `interval_s`, unaudited (request bytes are never published and run starts log at DEBUG). Boot load does not repeat the apply-time classing, so revoking one declaration fails only the runs that need it.

Residual, state-changing GETs. A GET step is read by method. The device cannot tell a GET that changes state (Shelly `GET /rpc/Switch.Set?on=false`) from a read, a job step cannot raise it with `access` (`BAD_JOB`), and `writes: "deny"` never fires on a request classed read. A step copied from a read GET to `/rpc/Switch.Set` would therefore be accepted at apply time and replayed every `interval_s`, with request bytes never published and run starts logged only at DEBUG. That would break the business rule that critical loads (running compressors, cold rooms) are never controlled. The control is in the cloud: the infra jobs tool (`energyme-home-iot-pipeline-lan-points` D13) accepts a GET step only when its method and path match the source driver's `READ_REQUESTS`, so a job set holding any other GET is never written. The device-side behaviour is accepted and stated as such in the spec. A stricter collector-only rule (a GET step also needs a read declaration) would close the gap on the device, but it changes the agreed path model and costs slots in the shared 8-entry list. It is an open decision for Jibril, not adopted here (Open Questions).

Ordering is the cloud's job: the infra jobs tool (`energyme-home-iot-pipeline-lan-points`) derives the read declarations from the driver's read requests and the job target, merges them into `system` desired `gateway_write_grants` with the target MAC, preserving every `kind: "write"` entry (owned by the control path), waits for the device ack and only then writes the job set. A set that arrives first is refused and re-sent.

### Worked example 1: Dixell XWEB history (site IT000010, device 9070698753dc)

Source `src_7f3a`, XWEB at 192.168.1.50:80 (placeholder IP), 25 controllers on RS485. One job reads the circular history of all wanted variables every 5 minutes with a 15-minute overlap and 6 hours of backfill. The password is the secret `xweb_pw`, set with `gateway_secret.py set --mac <xweb mac>` bound to `192.168.1.50:80` and to the XWEB MAC read from `net_scan`. The MAC is mandatory because the XWEB is on-link: an on-link slot without a MAC refuses every expansion with `SECRET_TARGET_MISMATCH` / `MAC_REQUIRED` (add-gateway-secrets), so the login step would fail on every run. Both POSTs are classed read by the stored, MAC-bound read declaration `{ip:"192.168.1.50", port:80, module:"http", kind:"read", mac:"<xweb mac>", allow:["POST /cgi-bin/login.lua","POST /cgi-bin/datachart.cgi"]}`, written by the cloud before the job set with the same MAC as the secret (D9); the steps carry no `access` field. The form field names and the session id delimiters below follow the pilot traces (task 1.3): `login.lua` answers JSON with the session at `user.sses`, so the capture takes the text after `"sses":"` up to the next `"`; `datachart.cgi` answers JSON keyed by the XWEB device id (1 to 25), which the cloud driver maps to `source_device`.

```json
 "session":{"ttl_s":1800,"expiry":{"status":[401,403],"marker":"login-screen"},
   "login":[{"id":"login","args":{"method":"POST","path":"/cgi-bin/login.lua",
     "headers":{"Content-Type":"application/x-www-form-urlencoded"},
     "body":"user=${var:user|url}&pass=${secret:xweb_pw|url}"},
     "captures":[{"name":"sses","from":"body","after":"\"sses\":\"","before":"\""}]}]},
 "steps":[{"id":"chart","args":{"method":"POST","path":"/cgi-bin/datachart.cgi",
   "headers":{"Content-Type":"application/x-www-form-urlencoded"},
   "body":"SSES=${cap:sses|url}&source=circular&startTS=${cursor}&stopTS=${now}&request=${var:req|url}"}}],
 "publish":"per_step"}]}
```

A run: if no session (or 30 minutes since login) the login step runs, its part is header-only (`ph:"login"`, `total`, `len:0`). The chart step expands `startTS` (window start) and `stopTS` (window end) as device UTC seconds; the pilot XWEB clock, measured about 1 h 24 min ahead, is corrected at the source (ideally NTP) before the job runs. In steady state the window is the last 5 minutes plus 15 minutes of overlap; after a reboot or outage it walks the 6-hour backlog one hour per run. If the XWEB answers with its login page (an expired session gets HTTP 200 with the web UI login page, which contains `login-screen`, not `login.lua`) or 401/403, the device logs in once and retries. The chart reply (text or binary, up to 128 KB) is published on `.../collector/src_7f3a` with `win`, `sha`, chunked above 48 KB. The cloud `dixell-xweb` driver decodes it into points `home/9070698753dc/src/src_7f3a/<address>/<var>` (e.g. `.../13/1` case air temperature, `.../13/4` setpoint) using the source device maps; overlap duplicates collapse on the point key. With `req` covering 25 controllers (variables 1 and 4 each), this job plus the Modbus job of example 2 measure about 1675 bytes as compact `doc` and about 1995 bytes once escaped into the shadow string, well inside the 5120 / 5632-byte budgets; task 4.1 measures the real delta on the device.

Commands during the run (support `http_request` to the XWEB UI) wait at most 8 s. If the tunnel is opened for the XWEB web UI, the job pauses and resumes after; the next window covers the gap.

### Worked example 2: Modbus TCP gateway with three meters

Source `src_9c1d`, a Modbus TCP to RS485 gateway at 192.168.1.60:502 with meters at units 3, 4 and 5. One job reads 60 holding registers from units 3 and 4 and 40 input registers from unit 5 every minute, as one batch.

```json
{"id":"mb_meters","rev":1,"enabled":true,"source_id":"src_9c1d",
 "target":{"ip":"192.168.1.60","port":502},"module":"modbus_tcp",
 "interval_s":60,"jitter_s":5,"step_timeout_ms":1000,"deadline_s":20,"max_bytes":256,
 "steps":[{"id":"u3","args":{"address":"u3/hr3000","count":60}},
          {"id":"u4","args":{"address":"u4/hr3000","count":60}},
          {"id":"u5","args":{"address":"u5/ir0","count":40}}],
 "publish":"batch"}
```

No time placeholders, so it runs before NTP (with `ts: null` until the clock is valid at publish) and while the cloud is down (into the out-queue). Each run gives three parts of 120, 120 and 80 raw bytes plus headers of about 300 bytes each, about 1.2 KB in one message on `.../collector/src_9c1d`: one 5 KB billing unit per minute, about 72 KB/h against the 2 MiB budget. An exception from unit 4 gives a header-only part with `rc: "MODBUS_EXCEPTION"`, `ps: 2`, and units 3 and 5 are still read. If unit 4 is powered off, the gateway lets the request time out: unit 4 gives a header-only `rc: "TIMEOUT"` part, units 3 and 5 are read, the run counts as successful and health shows `code: "TIMEOUT"`. The `generic-modbus` driver maps `u3/hr3000` and following registers through the unit's dated point map to `home/<device_id>/src/src_9c1d/u3/hr3000` etc.

## Risks / Trade-offs

- [The 10 s worst-case command wait looks like latency to support tools] → bounded and documented; the command still gets `IN_PROGRESS` at once from the MQTT task.
- [Internal heap pressure from the larger module buffers and a busy gateway task] → result buffers in PSRAM (`add-gateway-modules`), low-heap pause, bench tasks measuring internal heap floor, gateway and MQTT task stack high-water and PSRAM largest free block (D2, D4).
- [Silent delta drop above 9 KB] → cloud-side size check before write and the `reported.rev` lag alarm; device backstop on `doc` size.
- [Dropped parts on long outages for snapshot sources] → accepted (non-goal); `dq` in every header makes gaps visible.
- [Overlap duplicates cost bytes] → `overlap_s` is per job, default 0; the cloud dedups.
- [A cloud bug floods the LAN target] → interval >= 60 s, 8 jobs, 8 steps, run deadline, read-only jobs (as classed by the device, see the next entry), hourly budget.
- [A state-changing GET in a job is classed read and replayed every `interval_s`] → accepted device residual (D9); the infra jobs tool accepts GET steps only when they match the driver's `READ_REQUESTS`. A device-side rule is an open decision for Jibril.
- [An on-link secret set without a MAC] → every run fails at the login step with `rc: SECRET_TARGET_MISMATCH`, `rdt: MAC_REQUIRED` before any socket opens; the pilot reads the MAC with `net_scan` first and uses it for both the secret and the read declaration.
- [A login refused on the device is mistaken for a wrong password] → a login step keeps the executor's `st`, `rc` and `rdt` (for example `WRITE_NOT_ALLOWED` / `WRITES_DENIED` for a revoked declaration, `WRITE_NOT_ALLOWED` / `TARGET_MAC_CHANGED` for a swapped device), mirrored in health `code` and `detail`; `LOGIN_FAILED` is kept for a login reply that yielded no session.
- [The source clock steps back, or follows local DST] → windows come back empty with `st: "OK"`, the cursor moves past the data and the device raises no signal; only the cloud `date` drift check sees it, and the clock is then fixed at the source (D6). A source clock that follows local DST must be switched to UTC or NTP at the source.
- [The 256 KB ring cannot be allocated on a fragmented PSRAM] → allocated at boot when the switch is persisted on; a late enable that fails reports `wait` / `NO_MEMORY` per job and retries every 60 s (D4); task 4.8 measures the largest free block at a late enable.
- [Rule not deployed when a device enables the collector] → publishes to an absent rule are discarded; the collector is off by default and the infra change deploys rules and `KNOWN_SHADOWS` before any device is enabled.
- [Capture echoes outside the body] → accepted residual: the capture scrub covers the published body (every value the job holds, raw and in each encoding chain the job uses), not the `ct` and `date` header values copied from the reply, and values under 4 bytes are never scrubbed (the shared scrub minimum). A device that echoes a session id into its `Content-Type` or `Date` is not a realistic target; a 1 to 3 byte session value is not a credential.
- [Job table size] → the validated table is a fixed-size struct (about 30 KB with 8 jobs of 8 steps and 4 login steps each, plus a 12 KB string pool), larger than first estimated; it lives in PSRAM, one active and at most one pending, so it costs no internal heap.
- [Sibling changes evolve] → this change uses only the executor request/result fields, classifier, read declarations, `writes: "deny"` and per-call `Resolver*` named in `add-gateway-modules`, and the `${secret:x}` resolver of `add-gateway-secrets`; task 1.1 re-checks names before coding.

## Migration Plan

1. Infra first: `collector` in `KNOWN_SHADOWS`, Basic Ingest rules `energyme_{home,homepro}_{env}_rule_collector`, raw landing (infra change).
2. Firmware with the collector, off by default. Existing devices report a seventh shadow with `enabled: false`.
3. Dev devices (.174 Home, .80 Home Pro): set the mock XWEB secret with `--mac` (the mock is on-link), enable, apply both worked examples against bench targets, soak.
4. Pilot: read the XWEB MAC with `net_scan`, rotate the XWEB password and deliver it with `gateway_secret.py set --mac <xweb mac>` bound to the XWEB target, store the XWEB read declaration with the same MAC in `system` desired `gateway_write_grants` and confirm the device ack, apply the XWEB job, enable the collector on 9070698753dc, retire the cloud-side one-shot polling.

Rollback: set `enabled: false` (shadow or REST) or `gateway_enabled: false`; an older firmware ignores the `collector` shadow name (unknown shadows are never subscribed), and the cloud clears its desired state.

## Open Questions

- Exact XWEB login form field names, the `sses` delimiters and the hourly reply size (task 1.3); they change only the example job JSON and its `window_max_s` / `max_bytes`.
- Decision for Jibril: whether to add a collector-only device rule for GET steps (D9 residual), for example "a GET step needs a read declaration too". It closes the state-changing GET gap on the device but changes the agreed path model (GET read by method) and uses slots of the shared 8-entry list. Until decided, the infra jobs tool's `READ_REQUESTS` check is the only control.
- Decided 2026-10-31 (revised): no source clock offset anywhere, on the device or in the cloud. Source timestamps are taken as sent and a wrong source clock is fixed at the source (the pilot XWEB by the customer or EnergyMe, ideally with NTP) before its job is enabled; see ADR-0001 (`docs/adr/0001-solve-at-the-source.md`).
- Whether the AWS 8 KB named-shadow limit applies to `desired` and `reported` together or to each; the budget assumes together (conservative), so a looser reading needs no change.

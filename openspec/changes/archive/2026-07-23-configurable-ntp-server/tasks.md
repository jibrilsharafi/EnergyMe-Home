## 4. Hardware verification (bench device, before commit per CLAUDE.md testing rule)

**Done for 4.2, on 192.168.2.174 (2026-07-23) after removing the DHCP call.** OTA-flashed via local REST; device rebooted clean (`lastResetWasCrash: false`, no crash-analysis dump on boot), and logged `Initial time sync successful` ~6.1s after boot with no assert. Confirmed via `w32tm /stripchart /computer:192.168.2.1` that this bench network's gateway (192.168.2.1) does answer NTP, so this sync exercised the gateway-first path specifically (not just fallback). The 180s crash-monitor stability reset (`_crashResetTask`) also fired cleanly on this boot with no errors.

- [x] 4.1 Verify a device on a normal internet-connected network still syncs (gateway likely doesn't answer NTP, falls through to `pool.ntp.org`/Cloudflare IP) - no regression. Confirmed 2026-07-23: reconfigured 192.168.2.174 to join a phone hotspot via `POST /api/v1/network/wifi/credentials` (hotspot gateways don't run an NTP responder). Device reconnected and synced successfully with no errors/warnings. UDP log capture wasn't available on the new network, so this is a lower-fidelity confirmation than 4.2 (no captured timing to double-check it went through the fallback slots specifically), but a clean sync on a gateway that can't answer NTP is itself the regression check this task is after.
- [x] 4.2 Verify a device on a network whose router does answer NTP requests on its gateway IP syncs against the gateway (confirmed reachable on the bench network via `w32tm /stripchart /computer:192.168.2.1`). **Stronger direct proof, 2026-07-23:** with the bench router's WAN uplink physically disconnected (so `pool.ntp.org`/Cloudflare IP are unreachable), rebooted 192.168.2.174 and it still logged `Time sync successful` 2ms after `Syncing time...` fired - LAN-only response time, impossible if it had gone to the (now dead) fallback servers first. Confirms gateway-first, not just "gateway happens to also work".
- [ ] 4.3 Verify a device not yet WiFi-connected when `begin()` first runs (gateway `0.0.0.0`) degrades gracefully to the fallback servers instead of misbehaving. Not live-tested - the only way to force it is a boot-time WiFi race (e.g. deliberately wrong credentials at boot), which had no safe rollback available (no endpoint returns the current plaintext password to restore afterward), so left as accepted risk. Verified safe by code inspection instead: `_configureNtpServers()` (customtime.cpp:242-245) just formats `WiFi.gatewayIP().toString()` into a correctly-sized buffer with no branching - a disconnected gateway yields the literal string `"0.0.0.0"`, which is a well-formed (if unreachable) server address, not malformed input. SNTP fails that slot like any other unreachable server and falls through to `NTP_SERVER_1`/`NTP_SERVER_2`, the same mechanism 4.1 already exercises. No crash/hang path exists.
- [x] 4.4 Verify gateway-IP change (e.g. reconnect to a different bench network) is picked up on the next sync attempt with no stale state. Confirmed 2026-07-23 by the same hotspot reconnect as 4.1: `_configureNtpServers()` re-reads `WiFi.gatewayIP()` fresh on every call (no caching), and the device synced cleanly against the new network with no stale-gateway symptoms.
